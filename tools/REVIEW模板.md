# REVIEW.md 模板（审核标准卡）

> 由**该模块的 owner** 写，给审核方读；审核方先按它审，再单独核"有没有按它审"。
> 好的标准卡很短：说清**失败长什么样**、**必查什么**、**可以跳过什么**、**证据要什么格式**。

## 0. 范围与 owner

| 范围 | owner | 联系/决策人 |
|---|---|---|
|  |  |  |

## 1. 失败长什么样（按模块写"坏"的样子，不写"好"的样子）

- 教学内容：讲错数学 ／ 记号与正文不一致 ／ 答案键算不出 ／ 学生按题面算不出 ／ 图与数据对不上
- 前端：白屏 ／ 交互无反应 ／ 控制台报错 ／ 布局溢出 ／ 键盘/读屏不可用 ／ 资源 404
- 数据/科研：数字对不上 ／ 不可复现 ／ 结论超出数据 ／ 数据泄漏 ／ 环境未声明
- 其他：

## 2. 必查项（按风险）

| 风险 | 触发条件（按"改了什么"） | 必查 | 谁签 |
|---|---|---|---|
| 高 | 数学、答案键、判据/期望、CI/依赖/发布、安全相关 |  | 2 人（含 owner/用户） |
| 中 | 普通内容、图、交互 |  | 1 人 |
| 低 | 文档、文案、排版 |  | 机器全绿即可 |

## 3. 可跳过 / 不在审范围

- 明确不做：
- 已知假红（历史原因）：
- 只抽检不逐项：

## 4. nit 上限

- 默认 ≤ 3 条；超出只报一次 + 给"全库同类"结果，不逐处刷。

## 5. 证据格式（**必须可复核**）

- `file:line` + 命令 + 原始输出（或截图路径）
- 禁止："我看到"／"应该没问题"／"验算 ✓"（要中间量）
- 没跑/取不到 ⇒ 写 `2 没验成`，不是通过

## 6. 敏感路径（永远要人签）

- （例：`content/tasks/*.json` 答案键、`scripts/check-*.py` 判据、`.github/workflows/*`、依赖锁、发布脚本）

## 7. 总结格式

- 先给数字：发现 N 条（Blocker/Major/Minor/Nit）
- 无问题就明说："**没有需要修的**"
- 必写："这些检查会漏什么"

## 审核方自查（这张卡本身也要被审）

- 本轮有没有读 `REVIEW.md`？（会话审计：`--must-read 'REVIEW\.md'`）
- 必查项有没有真跑？（`--must-run '<必跑命令>'`）
- 同类发现有没有重复报？有没有按类扫全库？
